4. BUG TRIAGE GOVERNANCE

Authoritative source: the dedicated Bug Triage Jira export. It governs queue membership, Jira metadata, and snapshot comparison. Tempo, Weekly Capacity, and the general Jira PI Backlog export do not participate in Bug Triage.

Purpose: a current operational queue for Product and Engineering bug triage. It is not a KPI, forecast, throughput measure, delivery metric, or quality metric.

Team is governed exclusively by the Assignees CSV. If a Jira Assignee has no Assignees CSV mapping, the Jira Assignee remains visible, Team renders as `-`, and the queue row remains visible. Team is never derived from Jira or Tempo.

Snapshot comparison uses only distinct Jira Issue Keys from the latest and immediately previous Bug Triage exports. It reports:

- Current Queue
- Added to Queue
- Removed from Queue

These values represent snapshot comparison only. They must not be interpreted as Bugs created, fixed, closed, or resolved, or as Engineering throughput. The current export replaces the prior operational queue; historical bug-lifecycle analysis is outside MVP scope.

5. BUG SEVERITY DISTRIBUTION

Chart type: horizontal bar chart.

Authoritative source: current dedicated Bug Triage Jira export.

Approved rules:

- One distinct Jira Key equals one Bug; duplicate Jira Keys are ignored.
- Missing Bug Severity is excluded.
- Zero-count categories are hidden.
- Canonical severity order is preserved: Blocker, Critical, Major, Medium, Low, Enhancement.
- Bars use progressively lighter muted-red severity colors, with Blocker as the strongest shade.
- The shared snapshot banner appears immediately above the chart.

The chart is display-only, independent of global filters, Team and Assignee filters, Details search, and table sorting. It introduces no Bug Severity filter, KPI, calculation, reconciliation, or Tempo dependency.
