PROJECT STATE SUMMARY
- Dashboard architecture remains a static web app driven by generated `web/data.js` and rendered by `web/app.js`.
- Core governed semantics from v0.2 remain active:
  - Organizational/workforce Team is governed by Assignees CSV.
  - Capacity Team is governed by Weekly Capacity plus Assignees CSV.
  - Delivery Progress Team represents Jira ticket ownership.
  - Backlog Worked On Team represents Tempo contributor activity in the selected scope.
  - Week logic is governed by Master Date, not independent ISO logic.
  - TEMPO-106 and TEMPO-54 remain globally excluded from delivery analytics.
- The 01-Jul-2026 changes are primarily a UI/workspace upgrade and filter-surface expansion on top of the validated 30-Jun-2026 semantic baseline.

CALCULATION / DATA BEHAVIOR CHANGES
- Release cycle assignment is computed in `scripts/build_web_data.py` by matching Tempo worklog date to the release-cycle CSV start/end ranges.
- `filteredData()` in `web/app.js` now applies the new dimensions consistently across:
  - Tempo worklogs
  - Jira backlog
  - Backlog worklogs
  - capacity constraint logic
- Logged-effort KPI/chart calculations still intentionally ignore Jira Status by using `loggedEffortData()` built from `filteredData({ ignoreStatus: true })`.
  - This preserves the governed rule that Actual Hours and Team Utilization reflect centralized Tempo delivery effort rather than Jira status slices.
- Backlog detail rows continue to aggregate by distinct worked-on key using Tempo activity, but now preserve and render:
  - Priority
  - Target Release
  - Fix Version
- Delivery Progress rows continue to derive Team from Jira ownership, not Tempo contributor team, and still compute:
  - human-readable Days to Due
  - Delivery Health
  - terminal-status stop logic
- Parent inheritance remains active for child keys missing direct Jira rows:
  - inherited fields: Account, Delivery, Target Release, Fix Version
  - preserved fields: original child key and parent traceability
- Tempo operational items still render with planning placeholders and operational semantics.

BUSINESS RULES MODIFIED / CODIFIED
- No superseding business-rule reversal was introduced on 01-Jul-2026.
- The June 30 governance remains the active rule set and is now better surfaced by the UI:
  - Backlog Worked On is activity-based, not Jira inventory-based.
  - Delivery Progress is ownership-based and must respect Jira ticket ownership.
  - Team semantics are context-specific and must not be flattened across all tables.
  - Default status selection excludes Jira Done-category statuses.
- Additional codified implementation note:
  - Status filtering affects backlog/demand views and matched Jira-enriched worklogs, but must not reduce centralized Tempo-based Actual Hours / Team Utilization calculations.

BUG FIXES CARRIED FORWARD
- Delivery Progress Team ownership regression remains fixed.
  - Example validated scenario: `ADF-2326` must render under Integration ownership even though Tempo contributors include both Integration and Nexus.
- Delivery Progress Team filter leakage remains fixed.
  - Under Nexus filter, Integration-owned `ADF-2326` must not appear.
- Parent-child enrichment behavior remains fixed:
  - child key is preserved
  - Jira parent can enrich missing child metadata
  - child is not replaced by parent in rendered activity views
- Backlog and Delivery Progress continue excluding TEMPO-106 and TEMPO-54 from rendered delivery analytics.
- Default status logic remains governed by Jira status category, preventing Done-category rows from being treated as default active statuses.
